# Почему коллектор устроен именно так

## ReadOnlySpan и ReadOnlyMemory

`ReadOnlySpan<byte>` используется внутри синхронного парсера: это дешёвое представление участка памяти, которое не копирует байты. Span нельзя хранить в обычном объекте или передавать через `await`, поэтому результат содержит `ReadOnlyMemory<byte>`. Все его поля ссылаются на один арендованный datagram-буфер.

Буфер нельзя вернуть в pool сразу после парсинга: следующий арендатор перезапишет данные. Поэтому ownership проходит вместе с `LogEntry` через очередь и освобождается только после завершения записи batch. Тесты проверяют этот жизненный цикл.

## Bounded Channel

`Channel<T>` разделяет скорость UDP listener и SQLite writer. Ограничение `Capacity` задаёт максимальное число ожидающих записей и тем самым ограничивает память. Режим `Wait` выбран потому, что режимы `DropOldest`/`DropWrite` требуют особенно аккуратно освобождать owner отброшенного элемента. Для UDP ожидание не возвращает давление MikroTik — оно лишь переносит точку потери пакетов в socket buffer ОС.

У канала один producer и один consumer, поэтому включены `SingleWriter` и `SingleReader`. Это позволяет реализации убрать часть синхронизации.

## Batch по размеру и времени

Batch сбрасывается при первом из двух условий:

1. накоплен `BatchSize`;
2. с момента первого элемента прошёл `FlushInterval`.

Первое условие повышает throughput: один COMMIT обслуживает много строк. Второе ограничивает задержку при редком потоке логов. При ошибке batch остаётся владельцем буферов и повторяется; bounded channel в это время не позволяет памяти расти бесконечно.

## SQLite и Dapper

SQLite подходит для одного слабого хоста и одного writer. `journal_mode=WAL` позволяет Grafana или CLI читать базу параллельно с записью. `synchronous=NORMAL` уменьшает число дорогих fsync, сохраняя согласованность базы; при аварийном отключении питания могут потеряться последние WAL-транзакции.

Dapper выполняет параметризованный INSERT для набора строк внутри одной транзакции. Преобразование UTF-8 в `string` происходит только здесь: SQLite хранит текст, поэтому полностью избежать этой аллокации нельзя.

## Почему без Native AOT

Текущая версия использует Dapper, который строит и кеширует маппинг во время выполнения. Это плохо сочетается со строгим trimming/Native AOT. Docker поэтому использует небольшой chiseled runtime image, но обычную framework-dependent публикацию. Переход на AOT разумно делать только вместе с заменой Dapper на AOT-совместимый доступ к SQLite и отдельным набором publish-тестов.

## Границы текущей версии

- только UDP/IPv4 или конкретный IPv6 address из конфигурации;
- только BSD Syslog/RFC 3164, без RFC 5424;
- timestamp устройства хранится как исходный текст: в RFC 3164 нет года и timezone;
- гарантий доставки UDP нет;
- один SQLite writer; горизонтальное масштабирование потребует другого storage.
