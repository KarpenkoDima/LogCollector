# P0 Retrospective — что было сломано, что исправлено, чем доказано

Подробный разбор трёх критических дефектов из production-readiness аудита
(14 июля 2026). Документ для понимания, а не для отчётности. Каждый дефект
разобран по схеме: **симптом → корень → почему опасно → фикс → доказательство**.

---

## Контекст: почему вообще появился аудит

Проект получил две разные оценки, и важно понять, что они **не противоречат**
друг другу — они измеряют разные оси.

- Раньше: **9.5/10 за зрелость истории разработки**. Это про то, как проект
  делался — git-история, документация, тесты, ревью, культура коммитов.
- Теперь: **5.9/10 за production-готовность под нагрузку 10k/s**. Это про то,
  выдержит ли код заявленную нагрузку без потери данных и утечек.

Хороший код с прекрасной историей может иметь дыры под конкретную нагрузку.
Аудит нашёл три такие дыры уровня P0 — «исправить до любого запуска».

---

## Дефект P0.1 — вытеснение теряет буфер

### Симптом

Под устойчивой перегрузкой память растёт, `MemoryPool` постепенно
истощается, GC-давление увеличивается. Никаких исключений — тихая деградация.

### Корень

Канал был настроен так:

```csharp
Channel.CreateBounded<LogEntry>(new BoundedChannelOptions(10_000)
{
    FullMode = BoundedChannelFullMode.DropOldest,  // ← вот здесь
});
```

`DropOldest` означает: когда канал полон и приходит новая запись, самая
старая **молча выбрасывается**. Проблема в слове «молча».

Каждый `LogEntry` несёт `IMemoryOwner<byte> RawBuffer` — буфер, арендованный
из пула. Этот буфер нужно вернуть в пул через `Dispose()`. Но `Channel<T>`
— это generic-класс из стандартной библиотеки. Он не знает, что внутри
`LogEntry` лежит что-то, требующее освобождения. Он просто выбрасывает
структуру, и вместе с ней теряется единственная ссылка на арендованный буфер.

```
Канал полон [A][B][C]...[10000]
Приходит новая запись X
  → DropOldest выбрасывает A
  → A.RawBuffer НИКОГДА не вызовет Dispose()
  → буфер A не вернётся в пул — он потерян
```

### Почему это опасно именно под нагрузкой

При нормальной работе канал не переполняется — consumer успевает. Вытеснения
не происходит, дефект спит. Он просыпается ровно тогда, когда система под
давлением: burst трафика, медленный диск, инцидент на сети. То есть в худший
момент. Каждое вытеснение — минус один буфер из пула. Пул отвечает
аллокацией новых буферов в куче, GC работает чаще, latency растёт — и всё
это накладывается на уже имеющуюся перегрузку. Дефект усиливает проблему,
которая его вызвала.

### Почему нельзя было просто «настроить канал правильно»

`Channel<T>` — запечатанный класс. У него **нет** хука «сделай это при
вытеснении элемента». Значит встроенный `DropOldest` для владеющих ресурсом
элементов непригоден в принципе. Нужна была обёртка.

### Фикс — OwnedIngress

Создали абстракцию `IOwnedIngress`, которая делает вытеснение **явным**:

```csharp
public EnqueueResult TryEnqueue(LogEntry entry)
{
    lock (_enqueueLock)
    {
        // Быстрый путь: есть место — просто пишем
        if (_channel.Writer.TryWrite(entry))
            return EnqueueResult.Accepted;

        // Канал полон — вытесняем старейшего ЯВНО
        if (_channel.Reader.TryRead(out var evicted))
        {
            evicted.RawBuffer?.Dispose();      // ← вот здесь буфер возвращается
            Interlocked.Increment(ref _droppedCount);
        }

        _channel.Writer.TryWrite(entry);
        return EnqueueResult.DroppedOldest;
    }
}
```

Внутри — канал в режиме `Wait` (не DropOldest!), а drop-oldest реализован
руками: под `lock` читаем старейшего, диспозим его буфер ровно один раз,
пишем нового. `lock` делает последовательность «проверить-вытеснить-вставить»
атомарной — два писателя не могут вклиниться и вытеснить дважды.

Политика «freshest wins» сохранена: при перегрузке теряем старые данные, а
не блокируемся. Для UDP-мониторинга это правильно — важно текущее состояние
сети, а не то, что было минуту назад.

### Доказательство

Два теста:

```
OwnedIngress_EvictsOldest_AndDisposesItsBuffer_ExactlyOnce
  Канал ёмкости 1, пишем A, пишем B (вытесняет A)
  → assert: A.DisposeCount == 1   (буфер вернулся)
  → assert: DroppedCount == 1     (счётчик drops работает)
  → assert: выжила именно B

OwnedIngress_NoOverflow_DoesNotDisposeAnything
  Ёмкость 4, две записи, без переполнения
  → assert: ничего не диспознуто, DroppedCount == 0
```

Ключевой момент: тест **не запускает BatchWriterService**. Дефект живёт в
самом канале, вытеснение — внутри `TryEnqueue`. Убрав сервис, убрали все
гонки: тест падал (до фикса) и проходит (после) детерминированно.

## Дефект P0.2 — батчинг деградирует до размера 1

### Симптом

На реальном сетевом трафике каждая запись сохранялась отдельной транзакцией
SQLite, вместо накопления по 500. Пропускная способность в разы ниже
заявленной, диск молотит по одной записи.

### Корень

Старый цикл делал так:

```csharp
WaitToReadAsync(timeout)  // проснулись, как только пришла ПЕРВАЯ запись
while (TryRead(out e))    // выгребли всё, что УЖЕ в канале
    batch.Add(e);
SaveBatchAsync(batch)     // сохранили — и сразу начали новый цикл
```

Слово-ключ: **snapshot**. `WaitToReadAsync` просыпается на первой же записи.
`TryRead` в цикле выгребает то, что канал накопил **к этому моменту**. Если
записи приходят с зазорами (а сетевой трафик всегда с зазорами — дейтаграммы
не прилетают в одну наносекунду), то к моменту пробуждения в канале лежит
ровно одна запись. Выгребли одну, сохранили batch размера 1, повторили.

```
t=0мс   пришла запись 1 → проснулись → выгребли [1] → сохранили [1]
t=1мс   пришла запись 2 → проснулись → выгребли [2] → сохранили [1]
t=2мс   пришла запись 3 → проснулись → выгребли [3] → сохранили [1]
...
Результат: [1][1][1][1]... вместо [8][8][4]
```

На burst-трафике (500 записей уже в канале) дефект прятался: `TryRead`
выгребал все 500. Поэтому в тестах с мгновенной записью всё выглядело
нормально. Дефект проявлялся только на реальном потоке с зазорами.

### Почему это опасно

Заявленная цель — 10 000 записей/сек с батчингом по 500 = 20 транзакций/сек.
Деградация до batch-1 означает 10 000 транзакций/сек. Каждая транзакция
SQLite — это `fsync` на диск. 10 000 fsync/сек убивают любой диск и рушат
пропускную способность на порядок. Проект физически не смог бы держать
заявленную нагрузку.

### Фикс — окно накопления

Batch стал **окном**, которое открывается на первой записи и закрывается по
первому из четырёх условий: набралось `BatchSize`, истёк `BatchTimeout`,
канал завершился, или пришёл shutdown.

```csharp
// Фаза 1: ждём ПЕРВУЮ запись окна (без таймаута)
await WaitToReadAsync(stoppingToken);

// Фаза 2: окно с таймером ОТ первой записи
windowCts.CancelAfter(BatchTimeout);
while (batch.Count < BatchSize)
{
    while (TryRead(out e)) batch.Add(e);      // выгребли доступное
    if (batch.Count >= BatchSize) break;      // закрыто по размеру
    await WaitToReadAsync(windowCts.Token);   // ЖДЁМ добора в пределах окна
}
SaveBatchAsync(batch);
```

Разница в одном: после выгребания доступного, если batch ещё не полон, мы
**ждём следующую запись** в пределах окна, а не сохраняем немедленно.
Таймер стартует на первой записи, поэтому первая запись не задерживается
искусственно — окно живёт ровно `BatchTimeout` от её прихода.

Самая тонкая часть — два `catch` с фильтром:

```csharp
catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
    // это SHUTDOWN — flush и выход

catch (OperationCanceledException)
    // это TIMEOUT окна — flush partial, продолжаем
```

`when`-фильтр различает: сработал реальный shutdown или просто истекло окно.
Без этого различения нельзя понять, почему прервалось ожидание.

### Доказательство

```
Batching_EightRapidEntries_ShouldProduceExactlyOneBatchOfEight
  8 записей с зазором 1мс, BatchSize=8
  → assert: ровно 1 вызов repo, размер 8

Batching_TwentyEntries_ShouldProduceBatchesOfEightEightFour
  20 записей с зазором 1мс, BatchSize=8
  → assert: размеры batch-ей == [8, 8, 4]
```

До фикса `Actual` показывал `[1,1,1,1,...]` — это был диагноз в одну строку.
После фикса — стабильно `[8,8,4]`, без флаки, потому что 5-секундный timeout
на порядки больше 20мс разброса планировщика.

## Дефект P0.3 — потеря хвоста при остановке

### Симптом

При остановке сервиса записи, ещё не записанные в БД, могли потеряться.
Плюс риск double-dispose — освобождения одного буфера дважды.

### Корень

Тут дефект был не в «код неправильный», а в «код правильный, но не доказан».
Финальный drain при shutdown существовал:

```csharp
while (_reader.TryRead(out var entry))  // дочитываем остаток
{
    batch.Add(entry);
    ...
}
```

Но не было **теста**, доказывающего инварианты, которые требует аудит:
listener остановлен первым, ingress завершён, writer сохраняет хвост, после
StopAsync outstanding owners == 0.

Порядок остановки обеспечивается регистрацией:

```csharp
services.AddHostedService<BatchWriterService>();  // stopped last  — drains
services.AddHostedService<UdpSyslogListener>();   // stopped first — stops producing
```

`IHostedService` останавливаются в обратном порядке регистрации. Listener
второй → останавливается первым → перестаёт производить. BatchWriter первый
→ останавливается последним → успевает дренировать. Это корректно, но
недоказано.

### Почему это опасно

Потеря хвоста означает: при каждом рестарте сервиса (деплой, обновление,
перезагрузка) теряется до `BatchSize` последних записей. Для системы
мониторинга это данные ровно перед событием, ради которого мониторинг и
существует. Double-dispose ещё хуже — возврат одного буфера в пул дважды
может привести к тому, что пул отдаст один буфер двум потребителям, и данные
одного затрут данные другого. Это уже коррупция данных, а не потеря.

### Фикс

Кода-фикса как такового не было — shutdown-drain уже работал корректно,
а `Complete()` мы добавили в P0.1. Здесь «фикс» — это **доказательство**
корректности двумя тестами. Но чтобы доказать отсутствие double-dispose,
пришлось усилить инструмент:

```csharp
// Было — ловит только «не освобождён»
public bool IsDisposed { get; private set; }
public void Dispose() => IsDisposed = true;

// Стало — ловит и «освобождён дважды»
private int _disposeCount;
public int DisposeCount => Volatile.Read(ref _disposeCount);
public void Dispose() => Interlocked.Increment(ref _disposeCount);
```

Теперь assert `DisposeCount == 1` проверяет оба края: не 0 (leak) и не 2
(double-dispose).

### Доказательство

Два взаимодополняющих теста:

```
Shutdown_WithGatedRepository_SavesTail_AndDisposesEveryOwnerOnce
  GatedRepository блокирует первый SaveBatchAsync до release.
  Детерминированно оставляет хвост в канале на момент StopAsync.
  → assert: все 10 записей сохранены (хвост не потерян)
  → assert: каждый owner.DisposeCount == 1 (ни leak, ни double)

Shutdown_UnderLoad_LosesNothing_AndDisposesEveryOwnerOnce
  500 записей потоком с зазорами, резкий stop.
  → assert: все 500 сохранены
  → assert: каждый owner освобождён ровно раз
```

Gate-подход даёт детерминированное доказательство, нагрузочный —
реалистичное. Разные гарантии, оба ценны.

## Итог: что закрыто и что это дало

| Дефект | Было | Стало | Тестов |
|---|---|---|---|
| P0.1 | буфер теряется при вытеснении | явный Dispose вытесненного | 2 |
| P0.2 | batch деградирует до 1 | окно накопления | 2 |
| P0.3 | хвост не доказан, риск double-dispose | доказано тестами | 2 |

Всего 6 новых тестов, все зелёные, плюс 23 прежних не сломались = 29/29.

### Что изменилось в коде

```
Новое:
  IOwnedIngress.cs      — контракт owning-очереди
  OwnedIngress.cs       — реализация с явным drop-oldest

Изменено:
  BatchWriterService.cs — snapshot drain → окно накопления
  UdpSyslogListener.cs  — WriteAsync → TryEnqueue, + Complete() при shutdown
  ServiceCollectionExtensions.cs — регистрация IOwnedIngress вместо канала

Тесты:
  ProductionReadinessTests.cs — 6 regression-тестов
```

### Почему это regression guard, а не просто тесты

Эти 6 тестов не удаляются после фикса. Если кто-то в будущем вернёт
`DropOldest` на голом канале, или упростит батчинг обратно до snapshot-drain,
или сломает shutdown-drain — соответствующий тест покраснеет. Дефект не
сможет вернуться незамеченным. Красный тест из Этапа 0 стал вечным стражем.

## Чего ещё НЕ хватает до production-ready

P0 — это порог «до любого запуска». Мы его прошли. Но аудит определяет
production-ready выше — после закрытия P1:

```
P1.1  Изоляция SQLite от Loki (primary/secondary sinks)
      Сейчас Task.WhenAll связывает их судьбу — зависший Loki блокирует SQLite.

P1.2  HTTP lifetime — Dispose каждого HttpResponseMessage, timeout, retry-лимит.

P1.3  Валидация конфигурации при запуске — падать рано с понятной ошибкой,
      а не отправлять данные в никуда из-за опечатки в конфиге.

P1.4  Усиление парсера — обработка битых дейтаграмм без падения.
```

И P2 — эксплуатационная зрелость: метрики (received/parsed/saved/dropped),
retention SQLite, deployment hardening, документация.

Но три самых опасных дефекта — утечка памяти, деградация throughput, потеря
данных при рестарте — устранены и защищены. Это качественный переход:
из «работает на демо» в «не теряет данные под нагрузкой».
